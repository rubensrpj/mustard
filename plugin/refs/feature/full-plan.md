# /feature — Full-scope DECOMPOSE + PLAN

> You are here because `scope=full`. PLAN is the TERMINAL phase of /feature: materialise the plan, present it, STOP. EXECUTE unlocks ONLY after the user approves via `/spec` — NEVER emit `pipeline.stage: Execute` here. Approval also requires a prior CLARIFY (step 6): `approve-spec` refuses a Full plan until `<spec>/.clarified` exists AND records what was settled — settled terms or a stated reason, never a bare "done".

## DECOMPOSE

From the insumos + anchors, split the request into three natures (the judgement grain cannot make):

- Units with precedent → each maps to a matched slice. Only a net-new unit (CREATES an entity that does not yet exist) gets a `mustard-rt run scan spec` compile (`--like <sibling>` when one exists) — a create mold. An enhancement unit (modifies an existing entity) SKIPS `scan spec` and consumes the digest anchors (`context_enrichment`, pre-filled by `spec-draft` into the scaffold `context`).
- Cross-cutting invariants → contracts/hubs the repo already enforces (e.g. an injected `ICurrentTenant`); pass each via `scan spec --invariant <Name>` so the draft anchors the real wiring. NEVER invent the mechanism — mirror the anchored consumers.
- Net-new gaps (no precedent; `miss` after a repo-vocabulary re-query) → surface as a design decision; a `scan spec` draft never implies a precedent-less unit is safe to clone.

Concerns come from the digest — deterministic, no judge. `concerns` ≥2 → each is one unit above and maps to its own wave; a single concern needs no partition.

## Wave decision — 1-vs-N

Invariant: Full ⇒ ≥1 wave (parent = coordination doc, wave = executing subagent). This decides 1-vs-N, never zero — `decompose:false` still yields a single-wave plan (`totalWaves:1`), never a non-wave Full spec.

Reuse the `decompose`/`waves` `plan-prepare` returned in ANALYZE (multi-wave on `fileCount` / `layerCount≥2` / `newEntityCount`, else one). To recompute: `mustard-rt run scope-decompose --from-spec .claude/spec/{slug}/spec.md` (signals from the census; never pipe stdin — the `run` face never receives it).

Validate/derive `depends_on` from the import DAG:
```bash
mustard-rt run wave-dependency --plan plan.json
```
`--plan` reads a FILE — the only reliable transport (the `run` face gets no harness stdin; a pipe dies under `rtk`). Either shape works: `{"files":[…ANALYZE paths],"projectRoot":"."}` or the rich plan JSON below — the SAME plan.json the materialising call takes (`spec-draft --plan`, or `plan-materialize --plan` on a re-materialisation) validates here first. Cases: `cyclic-dependency` → warn + single-wave fallback + note in `## Concerns`; other `error` → fail-open to single wave; `{waves}` of 1 → genuine single layer (net-new with no edges auto-splits by role via `mustard.json#waveLayerOrder`); `{waves}` of 2+ → emit the rich `--plan` JSON and scaffold.

## PLAN — fixed materialisation order

Resolve Lang via cascade (`meta.json#lang` → `mustard.json#specLang` → AskUserQuestion once); hold it for `spec-draft --lang`. Headings, narrative rules, Component Contract: `${CLAUDE_PLUGIN_ROOT}/refs/feature/spec-language.md`. Each artifact exists before the next step consumes it:

1. Lapidate the body (no file yet). Per net-new unit: `mustard-rt run scan spec --entity {Unit} [--like {Sibling}] [--invariant {Contract}] [--ops create,...]` → a draft with the pattern menu, per-project sections, anchors, AC. An enhancement unit skips it, lapidating from the digest anchors. Read draft + anchors + request; resolve the bifurcation, prune, add domain rules, mark assumptions — in the project language/tone (`mustard.json#specLang` / `tone`). The draft's project-unit sections ARE the wave decomposition; hold in context.
2. Materialise the WHOLE layout in ONE call — AFTER the conversation material is assembled, never before (`/feature` §2.2). Fold the lapidated bodies into the plan JSON first (schema below; each wave carries `tasks`, `files`, `acceptance` and a `depends_on` already validated above) — never hand-author a wave body. Then: `mustard-rt run spec-draft --intent "<request>" --slug <the unit name the base gate reported> --scope full --lang <bcp47> --plan plan.json [--material .claude/.cache/spec-material.json] [--query-terms "<repo terms>"]` writes `.claude/spec/{slug}/spec.md` + `meta.json` (slug = the unit's ONE name: `--slug` when passed, else the slug half of the unit's branch, and only a draft no unit ever signalled falls back to `--intent`; `meta.json` is the single lifecycle source; `context` pre-filled with scan anchors) — and with `--plan` it does NOT stop there. The same call then runs, in-process, exactly the composite `plan-materialize` runs: the `wave-scaffold` renderer (each `wave-N-{role}/spec.md` gets `## Tasks`/`## Files`, plus the AC union into `wave-plan.md`) + `analyze-validation` (AC-format WARN) + **the NEGATIVE TEST over the parent `## Acceptance Criteria`** (the same engine `mustard-rt run ac-negative-check` publishes, composed in-process — do NOT run it separately on this path) + the `pipeline.scope` emit + emit-phase PLAN. So `spec.md`, `meta.json`, `wave-plan.md` and every wave directory come out of ONE invocation, with the proof taken in the same pass. `wave-scaffold` is a renderer, not a published command — these two composites are its only entry points. A refusal from the proof leaves NO layout behind, so a retry never meets a directory it did not create. Drop `--plan` (`[--waves N]` records the count and nothing else) and the call writes only `spec.md` + `meta.json`, leaving the layout to a step-3 re-materialisation. `--intent` is the TITLE (and the LAST-RESORT slug seed — see `--slug` above) — everything the conversation established (definitions, decisions with their reasons, findings with `file:line`) rides in through `--material` and lands in `## Definitions` / `## Decisions` / `## Evidence`; the channel is fail-closed, so a malformed material file aborts the draft instead of dropping it silently. If the raw words came back `weak`/`none` in ANALYZE, pass `--query-terms` with the code-terms that scored strong — else the draft repeats the weak query and withholds the enrichment. The ONLY scaffold writer. Routing gate: `spec-draft` re-classifies its own output and AUTO-DOWNGRADES an unjustified `--scope full` (single-layer, ≤5 files, no net-new) to light, rewriting `meta.json#scope` and reporting `scopeDowngraded:{from,to}` — trust it, return to Light EXECUTE; `--force-scope` honours full (audited as `pipeline.scope.override`). No-op on a placeholder census (`filesSectionEmpty`) — fill `## Files` first. Then fire-and-forget `mustard-rt run digest-adherence-finalize --spec {slug}` (telemetry; never blocks). **Finally — and this is not optional — `Edit` the lapidated bodies into the PARENT `spec.md`'s Plan-layer sections** (`## Files`, `## Boundaries`, and the rest); never overwrite, so the enriched `context` survives. The renderer fills the WAVE bodies from the plan JSON, never the parent's, so a spec that skips this ships `fill in affected files.` and `IN: ... OUT: ...` — the census `plan-prepare`/`classify_from_spec` read, and the boundaries every reviewer reads. Under the pre-fusion order this Edit rode along with step 3; the one-call door is where it belongs now (found in review, 2026-07-30).
3. RE-materialise — ONLY when the plan CHANGES after step 2. `plan-materialize` is the **RE-materialisation door**, no longer the first-materialisation one: it reconciles the layout onto an EDITED plan before approval — a decomposition the user reshaped, a criterion rewritten so it asserts the new behaviour, a Plan-layer body folded in by hand. `Edit` the lapidated bodies into the scaffold Plan-layer sections — never overwrite, so the enriched `context` survives — and fold every wave body into the plan JSON, never by hand after the scaffold. Then ONE call: `mustard-rt run plan-materialize --spec-dir <dir> --plan plan.json` — it runs the SAME in-process composite step 2 already ran (renderer + `analyze-validation` + the negative proof + the `pipeline.scope` emit + emit-phase PLAN), and being re-runnable is exactly what makes it the door for an edit. Never run the published steps separately. A FIRST materialisation does not come through here — step 2 did it in one call. It has exactly ONE other caller: the REPAIR pass after step 2's proof refused. That rollback removes the layout but deliberately leaves `spec.md` + `meta.json` standing (the criterion to fix lives in the first), so there is nothing left to draft and everything left to re-materialise — see step 4.
4. Act on validation — and on the proof. Read the `validation` the materialising call returned (step 2, or step 3 when the plan was edited); on `ok:false` append `issues[]` to `## Concerns` (non-blocking WARN). Then read `proof`: each criterion's own command was run against the tree AS IT IS NOW, before the work exists, and **clears only by coming back RED** — green, killed by its deadline, never attempted or still carrying an unfilled `<…>` placeholder is UNPROVEN (the trailing criterion is exempt: it is the build-green safety net). Unlike `validation`, this one BLOCKS: `proof.ok:false` makes that call exit 2 with `proof.unproven` (each id + the one action that clears it), the PLAN transition is WITHHELD, and no knob moves it — unconditional, like the AC-coverage gate above. Fix the criterion so it asserts the new behaviour — in the parent `spec.md`'s `## Acceptance Criteria`, which is what the proof reads, AND in the matching `acceptance` line of the plan JSON so the two do not drift — then re-materialise through **step 3's door**: `mustard-rt run plan-materialize --spec-dir .claude/spec/{slug} --plan plan.json`. Do NOT re-run `spec-draft` here: the rollback keeps `spec.md` + `meta.json` on purpose, so a second draft answers `output exists; pass --force to overwrite`, and `--force` re-drafts the body from scratch (it would discard the criterion you just fixed in `spec.md`, and everything else edited into it). Re-running an unchanged green command changes nothing. The verdict lands in `<spec>/ac-proof.json`, which `approve-spec` reads instead of re-running anything — so **on the Full path the operator never meets that refusal at the approval gesture**: it is already spent here, where planning waits anyway.
5. Concern Coverage Audit. Every concrete user critique maps to covered by wave/task | non-goal justified | surfaced for decision. Orphans block the approval question.
6. Clarify-finalize (F6). `mustard-rt run grill-capture --finalize --spec {slug}` records `<spec>/.clarified`, the marker `approve-spec` requires — and it must RECORD something: `--term "<term>"` per term the grill settled (repeatable), or `--reason "<sentence>"` stating why no grill applied (`glossary-coverage` hands you that sentence verbatim on `verdict:"declined"`). With NEITHER it refuses, and so does the approval: a marker that recorded nothing is a gate with no state of the world in which it fails. A complete-glossary spec still finalizes — with the reason that says so.

Spec layout — canonical section keys (EN, language-agnostic; heading localises per `specLang`): PRD layer `context`, `users`, `metric`, `non-goals`, `acceptance-criteria`; conversation channel `definitions`, `decisions`, `evidence` (written by `spec-draft --material`, absent when nothing was carried); Plan layer `entities`, `files`, optional `component-contract` (UI only), `tasks`, `dependencies`, `boundaries`. Materialisation split: the `wave-scaffold` renderer owns `wave-plan.md` + per-wave specs, and it runs inside whichever door materialises — `spec-draft --plan` on the first pass, `plan-materialize` on a re-materialisation; a `spec-draft` called WITHOUT `--plan` writes `spec.md` + `meta.json` and nothing else.

## Plan JSON schema

`spec-draft --plan` and `plan-materialize --plan` consume this (feeding the same `wave-scaffold` renderer):
```json
{
  "waves": [
    { "n": 1, "role": "backend", "summary": "one line",
      "depends_on": [],
      "tasks": ["wire the contract"], "files": ["src/api/handler.rs"],
      "acceptance": ["AC-1 — handler returns 200. Command: `curl -sf ...`"] },
    { "n": 2, "role": "frontend", "summary": "...",
      "depends_on": ["wave-1-backend"],
      "tasks": ["render the page"], "files": ["src/ui/page.tsx"],
      "acceptance": ["AC-2 — page renders. Command: `...`"],
      "reality_obligations": ["read the provider's official webhook doc for the retry semantics"] }
  ],
  "total_waves": 2, "lang": "pt-BR"
}
```
**`role` is not a free label — five names are RESERVED and pick a tool-restricted agent.** `plan` and `explore` resolve to read-only agents (no Edit/Write); `review`/`qa`, `guards` and `patterns` resolve to the plugin's read-only agents. Naming a WRITING wave `plan` hands it an agent that physically cannot write, while its rendered prompt still says "you implement" — the two halves disagree and the wave is spent producing nothing. Any other name (`backend`, `proof`, `discovery`, `bootstrap`, …) is a writing role. The canonical map is `${CLAUDE_PLUGIN_ROOT}/refs/agent-prompt/agent-prompt.md`.

`tasks` / `files` / `acceptance` are optional (a summary-only entry still scaffolds; no `tasks` emits a stderr WARN). ACs are EARS (`when/then` + a behaviour-asserting `Command:`), never a lone build-green; `analyze-validation` (in `plan-materialize`) WARNs on tautological build/test/grep ACs, AC↔wave/file gaps, and a test-shaped `Command:` with no `Expect:` (`test-ac-no-expect`). Optional `Expect: <regex>` (same line as `Command:` or the next): opt-in evidence — on exit 0 `qa-run` also requires the regex to match the combined **stdout+stderr** (a miss fails the AC despite exit 0; a malformed regex fails open). Omit it → legacy exit-0-passes. Trace waves to criteria with `satisfies` (AC ids), else `acceptance` lines — coverage is a gate: `plan-materialize` folds the parent `spec.md` `## Acceptance Criteria` ids into the traced set, so **every parent AC MUST be claimed by ≥1 wave**. An uncovered parent AC makes `plan-materialize` refuse the PLAN (exit 2 + `uncovered_acs`), unconditionally — the coverage gate has no mode knob. An untraced wave is always WARN, never blocking. `depends_on` MUST use the `wave-N-role` form (e.g. `["wave-1-backend"]`), never the bare role — an unresolved dep is dropped silently, flattening the DAG to one level. `plan-materialize` writes `wave-plan.md` (table + the localised AC union under `## Acceptance Criteria`, where QA reads) and each `wave-N-{role}/spec.md` (`## Summary` + `## Network` + materialised `## Tasks`/`## Files`); `agent-prompt-render --spec <wave-dir>` reads those back as the agent `## TASK` + `{reference_files}`. Headings render in the project language — do not hand-localise.

## Present + approve — STOP at PLAN

The materialising call (step 2, or step 3 on a re-materialisation) already emitted `pipeline.scope` + PLAN — do not re-emit. Print the spec verbatim + `wave-tree`. NEVER ask about a plan the user cannot see. Primary — plan mode: the wave-plan (+ spec body) IS the plan file; `ExitPlanMode` acceptance mints `<spec>/.approved-by-user` (the marker `approve-spec` requires). Fallback (no plan mode): print the spec, attach `wave-plan.md` as the AskUserQuestion `preview`:

- "Approve wave plan for later" → STOP; user runs `/mustard:spec {letter}` (new session, which asks for the approval there) or `{letter}r` (the typed form IS the approval — it mints `<spec>/.approved-by-user` and goes straight to wave 1, with no second gesture).
- "Edit decomposition (hint PLAN)" → user gives a hint (e.g. merge waves 2 and 3); re-decompose once.
- "Reject decomposition" → `mustard-rt run wave-collapse --spec {spec} --mode full` (the reject path — `${CLAUDE_PLUGIN_ROOT}/refs/spec/resume-loop.md § A`). NEVER a non-wave Full spec.

PLAN is terminal — the only approval that unlocks EXECUTE is the event `/spec` emits (see Inviolable). On "Approve and implement?", direct the user to `/spec`.

## COORDINATE — parent/epic specs

A spec with `children_specs.length > 0` may enter COORDINATE: the orchestrator tracks children, it does NOT implement. `mustard-rt run emit-phase --spec {epic} --to COORDINATE` after linking; when all children reach CLOSE, `mustard-rt run emit-phase --spec {epic} --to CLOSE`.

## Inviolable rules (Full)

- Full STOPS at PLAN and REQUIRES `/spec` before any EXECUTE. /feature must NEVER emit `pipeline.stage: Execute`, dispatch, Edit, or Write production code for a `scope=full` spec — `scope_guard` enforces it.
- The scaffold — and, with `--plan`, the whole wave layout — is materialised ONLY by `mustard-rt run spec-draft`; `plan-materialize` re-materialises it onto an edited plan. Fold `scan spec` bodies in with `Edit`. NEVER hand-write `spec.md`, NEVER hand-author a wave body after the renderer has written it — emit it in the plan JSON.
- ALWAYS compile each net-new unit with `mustard-rt run scan spec` (create-only mold); an enhancement unit consumes the digest anchors.
- The locator is 100% deterministic — the digest (and `scan spec` for net-new) is the whole research step; NO judge layer. NEVER dispatch a model to re-rank, partition, or validate it — work from the flat anchors (pruned by provenance) and `concerns` when ≥2. That research covers the CODEBASE and nothing else: when a wave's correctness depends on something the repository cannot answer — a provider's official semantics, a live endpoint's real response, the actual shape of a stored row — declare it as a `reality_obligations` entry on that wave (see the schema above) instead of writing it as prose and hoping it is read. `plan-materialize` materialises each duty into the wave's `## Reality Obligations` with its own `RO-{n}.{i}` id, `agent-prompt-render` delivers them as the prompt's `## REALITY OBLIGATIONS` section (instructing the agent to account for each BY ID in its report), and `wave-done` names every id no text the wave recorded accounts for. That last step reports the RECORD, never the world: an unaccounted duty is "nobody said", not "nobody checked" — it prints and never blocks.
